# Activity 1 – Step 2: A specific prompt with context

**Chatbot / model:** <!-- e.g., ChatGPT (GPT-5), Gemini, Claude / เช่น ChatGPT (GPT-5), Gemini, Claude -->

## Prompt

```text
Act as a professional software tester and suggest test ideas for the feature delimited by three hashes. All test ideas should be focused on discovering risks that impact the quality characteristics: Functionality, Data Integrity and Security
###
* As a paralegal, in order to store and share legal documents, I want to be able to securely upload documents.
* Acceptance criteria:
  - Upload should support the following common file formats: PDF, DOCX, TXT
  - The maximum file size should be 20MB
  - When a document is uploaded it should give a progress update to the user
  - Once uploaded, the document must initially be only accessible to the person who has uploaded it
  - A report of the upload and whether it was successful or not will be stored in the auditing feature
###
```

## Response

Here is a structured test strategy for the legal document upload feature, focused specifically on **Functionality**, **Data Integrity**, and **Security**.

---

## 1. Functionality Testing

Ensures the upload feature operates according to functional specifications, UI behaviors, and progress reporting.

### Supported File Formats & File Sizes

* **Supported Types:** Validate successful upload of `.pdf`, `.docx`, and `.txt` files.
* **Format Case Sensitivity:** Upload legal files with uppercase/mixed extension names (e.g., `CONTRACT.PDF`, `brief.Docx`, `notes.TxT`).
* **Boundary Value Analysis (File Size):**
* **0 Bytes:** Attempt to upload empty `.txt`, `.docx`, or `.pdf` files. Verify clear validation message preventing empty uploads.
* **1 Byte to 19.9 MB:** Upload valid legal files below the limit.
* **Exactly 20 MB:** Upload a file sized precisely at $20 \times 1024 \times 1024$ bytes ($20,971,520$ bytes).
* **20 MB + 1 Byte / 20.1 MB:** Attempt to upload files slightly above the limit. Verify client-side and server-side rejection with clear user messaging.



### Progress Updates & UX State

* **Real-Time Progress Accuracy:** Verify progress bar or percentage indicator increases dynamically and accurately ($0\% \rightarrow 100\%$) during upload on varying network speeds.
* **Network Interruption / Resumption:** Simulate network failure during active upload. Verify the user is notified, progress halts gracefully, and retry/resume behavior operates cleanly without duplicate partial uploads.
* **Cancellation Mid-Upload:** Cancel the upload at $50\%$. Verify process halts immediately, UI resets, and no orphan payload remains staged on the server.

---

## 2. Data Integrity Testing

Ensures file contents, metadata, and audit records remain complete, accurate, and untampered with.

### File & Storage Integrity

* **Binary Consistency / Hash Verification:** Compare SHA-256 / MD5 hashes of the local file before upload and the stored file after download to guarantee zero bit corruption during upload or processing.
* **Encoding & Special Characters:** Upload `.txt` and `.docx` files containing multi-language legal scripts, special characters (e.g., `§`, `©`, `¶`, non-ASCII, emojis), or complex formatting/embedded tables. Verify non-corruption upon re-download.
* **Filename Handling:**
* **Special Characters in Filename:** Upload files with names containing punctuation and symbols (e.g., `State_v_Smith_#12-34(v2).pdf`).
* **Long Filenames:** Upload files with filenames exceeding 200+ characters to test database field constraints and storage path truncation.
* **Duplicate Filenames:** Upload `brief.pdf`, then upload another distinct file named `brief.pdf` by the same user. Confirm versioning or conflict resolution (e.g., `brief(1).pdf`) without overwriting or corrupting original file data.



### Auditing & Reporting

* **Successful Upload Audit Logs:** Verify that every successful upload creates an audit entry containing correct metadata: timestamp, user ID (paralegal), filename, original file size, and success status.
* **Failed Upload Audit Logs:** Trigger upload failures (e.g., size exceeded, unauthorized format, server timeout). Verify the audit log records the failure event, failure reason, timestamp, and user context.
* **Audit Record Immutability:** Verify that audit entries cannot be edited, deleted, or bypassed by the paralegal or standard system roles.

---

## 3. Security Testing

Guarantees document confidentiality, strict access controls, and resistance to malicious payloads.

### Access Control & Confidentiality (Initial Isolation)

* **Default Access Control (Creator Only):** Upload a document as Paralegal A. Attempt to access or download the document via direct URL/API endpoint while logged in as Paralegal B, Attorney A, or an unauthenticated user. Verify access is strictly denied (`403 Forbidden` / `404 Not Found`).
* **Multi-Tenant / Session Isolation:** Verify that session swapping or opening concurrent tabs across different user accounts does not leak uploaded file IDs or temporal access tokens.
* **Direct URL Scraping / IDOR (Insecure Direct Object Reference):** Attempt to guess or enumerate document IDs/URLs (e.g., `/documents/1001` vs `/documents/1002` or manipulating GUID parameters) to access other users' initial uploads.

### Payload & Content Validation

* **Extension Spoofing (MIME Type Check):** Rename an executable file to `.pdf` (e.g., `malware.exe` $\rightarrow$ `malware.pdf`). Verify the system uses true file header/magic-byte inspection to reject the file rather than relying on extension matching.
* **Embedded Script / XSS:** Upload an HTML or SVG payload disguised as or embedded within a `.txt` or `.docx` file containing malicious JavaScript (`<script>alert(document.cookie)</script>`). Verify the application sanitizes or forces file download headers (`Content-Disposition: attachment`) rather than inline rendering.
* **Path Traversal Attacks:** Upload a file named `../../../../etc/passwd` or `..\..\..\boot.ini`. Verify file paths are sanitized and forced into designated secure storage buckets.
* **Unauthenticated API Access:** Attempt calling the upload endpoint without a valid authorization token / session cookie to ensure `401 Unauthorized` responses.
